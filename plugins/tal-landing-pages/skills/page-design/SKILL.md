# שלב 3 — עיצוב

קודם לקרוא ולעבוד לפיהם:

- החוקה: `<Base directory של הסקיל הזה>/../../references/stage-contract.md`
- עקרונות העיצוב (מיתוג, פריסה, RTL, טיפוגרפיה, ניגודיות, "נראה כמו תבנית?"): `<Base directory של הסקיל הזה>/../../references/design-principles.md`
- כללי הכתיבה, בשביל סעיף 6 (דפוסי AI) בכל הודעה לבעל העסק: `<Base directory של הסקיל הזה>/../../references/writing-rules.md`

ובכל תת-שלב, הקובץ שלו (כתוב בראש התת-שלב). אחרי שיש `site/`, גם `site/TEMPLATE.md` של הדף. מה שכתוב שם על התבנית גובר על כל השאר, כי הוא מתעדכן יחד עם הקוד.

## נתיבים ושמות בפקודות

- `$SCRIPTS` = `<Base directory של הסקיל הזה>/../../scripts` (התיקייה). זה **קיצור בלבד**, לא משתנה של הטרמינל. משתנים לא עוברים מפקודה לפקודה, אז בכל פקודה כותבים את הנתיב המלא, למשל: `node '<Base directory של הסקיל הזה>/../../scripts/status.mjs' …`.
- `<האתר>` = `<תיקיית הדף>/site`, נתיב מלא.
- כל נתיב, שם או הערה בפקודה עוטפים בגרש בודד: `'דנה בע"מ'`.
- נתיב או שם שיש בו גרש (') — לכתוב אותו כ-`'\''`. למשל `צ'יפס` נכתב `'צ'\''יפס'`.
- **פקודות npm רצות עם `--prefix`, בלי `cd`:** `npm --prefix '<האתר>' run build`. הסקריפט רץ מתוך `<האתר>`, אז גם `npm --prefix '<האתר>' run images -- …` עובד. במקורות של תמונות כותבים נתיב מלא.
- **מחיקה רק עם node,** לא עם `rm`: `node -e 'require("fs").rmSync(process.argv[1],{recursive:true,force:true})' '<נתיב>'`. מוחקים רק מה שהשלב הזה יצר (דף התצוגה של המיתוג), אף פעם לא קובץ של בעל העסק.

## איך מדברים עם בעל העסק

- **פנייה:** לפי "פנייה לבעל העסק" ב-CLAUDE.md. לא מולאה → ברבים. ההודעות לדוגמה בקבצי ההפניה כתובות ברבים או בזכר, ומתאימים אותן.
- **כל הודעה לבעל העסק בעברית,** גם עדכון קצר באמצע עבודה ("עכשיו אני בונה את דף ההשוואה"). לא באנגלית.
- **שפה פשוטה.** בלי מונחים כמו קומפוננטה, build, שרת, JSON, config. אם אין ברירה, מסבירים במילים של בעל עסק ("קובץ ההגדרות של האתר"). שמות קבצים רק כשבעל העסק צריך לזרוק משהו לתיקייה.
- כל הודעה, גם רגילה, עוברת את דפוסי ה-AI האסורים בסעיף 6 של writing-rules.md.
- **שאלה אחת בכל הודעה.** בסוף כל תת-שלב: מראים, ושואלים "מאשרים, או משנים משהו?".
- **אישור שכבר כתוב בהודעה של בעל העסק** ("מאשר כל שלב", "אין לי רפרנסים") נחשב תשובה לנקודה שהוא מתאר. עדיין מראים את התוצאה, רושמים את האישור בהערה, וממשיכים. **שלושה מקומות שאישור מראש לא חל עליהם, ושם תמיד עוצרים, מראים ומחכים לתשובה:**
  - **בחירת הכיוון מתוך שלושה (3א.3).** בעל העסק צריך לראות את שלושת הכיוונים כדי לבחור. גם "תבחר אתה" או "תבחר את הראשון" שנאמרו לפני שראה אותם לא נחשבים בחירה: מראים, ושואלים.
  - **התמונות (3ג).** אילו תמונות נכנסו לדף, ואיך נראות התמונות המטושטשות, בעל העסק רואה ומאשר בעצמו. אלה התמונות שלו ושל הלקוחות שלו.
  - **כסף:** יצירה ב-Higgsfield דורשת "כן" נפרד, באותו רגע, אחרי הודעת העלות.

## א. איפה אנחנו

לפי צעד 1 בחוקה: `node '$SCRIPTS/scaffold.mjs' find-root '<התיקייה הנוכחית>'` (ואם לא נמצאה, `find-below` והודעת "פותחים מחדש"), ואז `node '$SCRIPTS/status.mjs' list '<תיקיית העסק>'` ובחירת הדף.

## ב. תנאי כניסה

1. `node '$SCRIPTS/status.mjs' next '<תיקיית הדף>'`. הפלט הוא השלב הראשון שעוד לא אושר.
   - `start` → לעצור: "קודם מסיימים את ההכנה. מקלידים `/page-start`."
   - `brief` → לעצור: "קודם מסיימים את האפיון. העיצוב בנוי על מה שהדף אומר, ובלי אפיון עוד אין לו מה להגיד. מקלידים `/page-brief`."
   - `copy` → לעצור: "קודם מאשרים את הקופי. בונים דף סביב טקסט סופי, כמו שבונים קירות לפי תוכנית. עיצוב לפני קופי נבנה פעמיים. מקלידים `/page-copy`."
   - `design` → ממשיכים.
   - שלב אחר, או `null` → העיצוב כבר אושר. לשאול: "העיצוב של הדף הזה כבר אושר. לפתוח אותו מחדש?" כן → `node '$SCRIPTS/status.mjs' set '<תיקיית הדף>' design doing 'נפתח מחדש: <למה>'`, לשאול איזה תת-שלב רוצים לשנות, ולעבוד רק עליו. לומר שאחרי השינוי כדאי לעבור שוב על `/page-check`. לא → לעצור ולתת את הפקודה של השלב הבא.
2. `node '$SCRIPTS/status.mjs' set '<תיקיית הדף>' design doing` (בלי הערה, כדי שההערה של "איפה עצרנו" תישמר).

2. לקרוא, לפני כל שאלה:
   - `CLAUDE.md` של העסק: מה העסק עושה, למי, שתי שורות הפנייה, "החלטות" (שם יכול להיות כתוב צבע או סגנון).
   - `brand/brand.md`, ו-`ls` על `brand/logo/`, `brand/photos/`, `brand/proof/`.
   - `1-brief/brief.md`: בעיקר למי הדף (סעיפים 4–5), הכאב והתוצאה (7, 9), הפעולה האחת (3), ומה כבר מצאנו ברשת (סעיף 1: צבעים, כתובת הלוגו). התחושה שבעל העסק רוצה לא נשאלת באפיון: היא ב-`brand/brand.md` › "תחושה במילים", ואם שם ריק, נקבעת ב-3א.

   - `2-copy/images-list.md`.
   - `3-design/design.md` ו-`3-design/references.md`.
   - ההערה של שלב העיצוב: `node '$SCRIPTS/status.mjs' show '<תיקיית הדף>'`.
3. **לא שואלים מה שכבר כתוב באחד מהם, או מה שנאמר בשיחה.**

## ה. 3א מיתוג

### 1. האתר עצמו (פעם אחת, ממש בהתחלה)

גם דף התצוגה של המיתוג צריך אתר שרץ, אז זה קודם לכול.

- `ls '<האתר>/node_modules'` נכשל → קודם לומר לבעל העסק במשפט אחד: "עכשיו אני מתקין את חלקי האתר. זה לוקח דקה או שתיים, ולא צריך לעשות כלום בינתיים." ואז `npm --prefix '<האתר>' install`.
  - נכשל בגלל אינטרנט → לומר את זה בפשטות, ולבקש לבדוק את החיבור ולהקליד שוב `/page-design`. לא ממשיכים בלי זה.
  - `node -v` מתחת ל-22.12 → לומר שצריך לעדכן את Node (שורה אחת: להוריד את הגרסה המומלצת מ-nodejs.org, להתקין, לסגור ולפתוח את קלוד), ולעצור.
- לקרוא את `<האתר>/TEMPLATE.md` כולו. בעיקר: "אסור להוריד", "מה כל שלב עורך", "הטקסטים של הדף", "מצב עריכה", "תמונות".

### 2. מאיפה המיתוג

לפי סדר החיפוש בסעיף 1 ב-design-principles.md. עוצרים במקור הראשון שנותן תשובה מלאה.

- **יש מיתוג מלא** (ב-brand.md, ב-CLAUDE.md, מלוגו או מאתר קיים) → מעבירים אותו כמו שהוא. צבע שלא עובר ניגודיות כפתור: לפי סעיף 2 שם (המקור נשאר ל-`accent`, גרסה כהה יותר ל-`primary`), ומסבירים במשפט אחד למה. מראים את הפלטה ואת הפונטים, ושואלים לאישור.
- **מיתוג חלקי** → משלימים רק את מה שחסר, ומראים את ההשלמה.
- **אין כלום** → שאלה אחת לפי סעיף 1.4 ("יש לכם צבעים או לוגו?"). התשובה "אין" (או שכבר כתובה בהודעה) → 3 כיוונים.

### 3. שלושה כיוונים (רק כשאין מיתוג)

1. בונים 3 כיוונים שונים באמת, לפי סעיף 3 (שם, תחושה, 5 צבעים, זוג פונטים מהטבלה המותרת, למי זה מתאים מתוך הבריף).

3. כותבים את `<האתר>/app/brand-preview/page.tsx` לפי השלד בסעיף 3 (כולל `robots: { index: false, follow: false }`), עם הכיוונים שלנו, והכותרת וטקסט הכפתור **האמיתיים** מ-copy.md. הפסקה הקצרה: משפט אמיתי מהקופי, לא טקסט לדוגמה.

### 4. שומרים את הבחירה

לפי הטבלה בסעיף 4 ב-design-principles.md:

- `brand/brand.md`: חמשת הצבעים, הפונטים, התחושה, "מה לא", ו"מאיפה זה בא". מתקנים את התווית "צבע הדגשה (כפתורים)" ומוסיפים שורה לצבע הטקסט, כמו שכתוב שם.
- `<האתר>/site.config.ts` → `brand`: חמשת הצבעים, hex מלא (`#RRGGBB`).
- פונט שאינו Rubik → `app/layout.tsx` ו-`app/globals.css` בדיוק כמו בסעיף 4 (שם משתנה שונה מהשם ב-`@theme`). **מחליפים את שני המשתנים ב-`@theme`: `--font-sans` (טקסט) וגם `--font-heading` (כותרות).** כל `h1`–`h4` באתר מקבלים את `--font-heading` מהתבנית עצמה, גם בחלקים הקבועים (דף התודה, הדפים המשפטיים, באנר העוגיות, 404), אז לא צריך לשים class על כל כותרת. מחליפים רק את `--font-sans`? הכותרות בחלקים הקבועים יישארו ב-Rubik. נשארים עם Rubik → לא נוגעים.
- `CLAUDE.md` → "החלטות": `<תאריך> · מיתוג: <שם הכיוון> · <למה>`.
- `3-design/design.md` → "מיתוג" ו"פונטים", כולל יחסי הניגודיות שנבדקו.
- **דף התצוגה נמחק:** מחיקה עם node (ראו "נתיבים"), ואז `ls '<האתר>/app/brand-preview'` חייב להיכשל.
- **בודקים שזה באמת השתנה:** פותחים את הדף (ט) ומוודאים שהכפתור בצבע החדש. ערך לא תקין ב-config נזרק בשקט וחוזרת ברירת המחדל. הקבצים השתנו והדף עדיין בצבע הישן? עוצרים את השרת שרץ ברקע ומריצים אותו מחדש (לפעמים הוא לא קולט שינוי ב-config או ב-layout), ובודקים שוב.
- `node '$SCRIPTS/status.mjs' set '<תיקיית הדף>' design doing '3א מיתוג אושר'`.

### 3. סקשן לכל סקשן

- קובץ לכל סקשן ב-`<האתר>/components/sections/`, בשם באנגלית לפי הטבלה (`Hero.tsx`, `Without.tsx`, `Learn.tsx`…). כל קובץ:
